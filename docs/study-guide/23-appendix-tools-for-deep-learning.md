# 第 23 章 附录：深度学习工具重点解析

[返回解析目录](README.md) · [原章目录](../../chapter_appendix-tools-for-deep-learning/index.md) · [术语对照表](../GLOSSARY.zh-CN.md)

## 本章定位与先修

工具附录回答如何运行 Notebook、使用远程计算、选硬件、贡献源码以及查阅 `d2l` 工具。它不是算法章节，学习目标是建立可靠的工作流程：文件属于哪个环境、代码由哪个内核运行、输出何时生成、结果如何保存。

本仓库已部署独立 PyTorch 学习环境与教材网站，具体启动、访问和依赖以 [当前部署说明](../../deployment/README.zh-CN.md) 为准。原书云平台截图、实例选择、CUDA 安装命令反映教材编写时的流程；本文只解析其结构，不将其当作已核验的当前云产品操作指南或价格信息。

## 核心关系

浏览器只是 Notebook 的交互界面，实际 Python 代码在内核（kernel）进程中运行；该内核所在环境决定可导入的库和可见 GPU。教材静态网页（static website）展示内容，JupyterLab 提供可执行学习环境，两者用途不同。

可以用“源码 → 文档构建 → 网站”与“源码 → 练习副本 → 内核执行 → 输出”两条路径理解本部署。静态页面能够打开，不证明所有训练已完成；Notebook 留有旧输出，也不证明当前内核和依赖还能复现它。工具选择最终要服务于可追踪的输入、配置和结果。

## 按教材顺序逐节解析

### 23.1 使用 Jupyter Notebook

[原文与代码](../../chapter_appendix-tools-for-deep-learning/jupyter.md)。Notebook 由代码、Markdown 与执行输出构成，适合将推导和实验放在同一文档中。内核会保留变量，按任意顺序运行单元格可能形成屏幕上不易察觉的依赖；整理实验时应确认从干净内核按顺序运行的逻辑。

本节还介绍 Markdown 支持、远程访问及计时。远程浏览器和服务器不是同一进程环境，`127.0.0.1` 指向访问所在主机；本部署通过 Jupyter 的 `/book/` 入口复用已可访问通道。计时时要区分首次下载/初始化与稳定训练阶段，涉及异步 GPU 运算时还应留意同步边界。

### 23.2 使用 Amazon SageMaker

[原文](../../chapter_appendix-tools-for-deep-learning/sagemaker.md)。本节按注册、创建 Notebook 实例、运行与停止、更新教材组织流程。核心是托管计算环境与持久文件的生命周期，浏览器关闭不等于实例停止；实例中的 Notebook 也有自己的内核和依赖。

在当前服务器学习无需另开云实例，直接使用现有 Jupyter 即可。本解析未创建、登录或核验 SageMaker 资源；原文界面和命令需要在实际迁移时对照当前官方说明，不能据此声称云环境已部署成功。

### 23.3 使用 AWS EC2 实例

[原文](../../chapter_appendix-tools-for-deep-learning/aws.md)。本节把区域/配额、实例启动、SSH 连接、CUDA 和 Python 库安装、远程 Jupyter、关闭实例串成完整基础设施流程。重点是明确各命令在哪台机器执行，以及驱动、计算库、Python 环境各自的职责。

本项目已有隔离环境与支持当前 GPU 的 PyTorch，具体版本由部署约束记录；不需要为学习本节照抄原文旧安装命令。SSH 端口转发将本机端口映射到服务器服务，不改变服务实际运行位置；访问问题应分别检查服务进程与网络通道。

### 23.4 使用 Google Colab

[原文](../../chapter_appendix-tools-for-deep-learning/colab.md)。Colab 提供浏览器中的远程 Notebook，降低开始实验的环境准备成本，但其运行时与当前服务器不是同一个文件系统。迁移练习要同时准备依赖、数据路径与保存方式，不能只复制一段训练代码。

本解析不保证某种加速器、运行时长或套餐权益；这些属于实际使用时需要核验的平台条件。对当前任务，现有服务器的学习副本是直接可用的工作位置。

### 23.5 选择服务器和 GPU

[原文](../../chapter_appendix-tools-for-deep-learning/selecting-servers-gpus.md)。硬件选择需要联合考虑计算吞吐、显存、CPU、内存、存储和网络。显存决定模型、优化器状态与激活能否装下，数据读取或 CPU 预处理也可能让 GPU 等待；仅比较显卡名称或理论算力不足以判断训练速度。

当前部署说明记录本机设备及已完成的基础验收，不能扩展为全书性能基准。并行学习实验应先区分“独立任务可并行”与“同一 GPU 被过量争用”，合理控制数据加载进程和线程数。

### 23.6 为本书作贡献

[原文](../../chapter_appendix-tools-for-deep-learning/contributing.md)。本节区分小修订、大改动提案和完整提交流程，介绍 Git、GitHub、克隆、编辑、推送与拉取请求（pull request）。Git 提交记录本地变更，推送同步远端，拉取请求用于请求上游评审，它们是不同动作。

当前仓库的用户远端与官方上游用途不同：把学习材料推到自己的仓库，不等于已向官方提交或被接收。修改文档时应保持源文结构与许可信息，新增解析与原稿分离，并准确说明验证范围。

### 23.7 实用函数与类

[原文与代码](../../chapter_appendix-tools-for-deep-learning/utils.md)。这一节集中收录多个章节使用的辅助函数，包括数据加载、训练循环、指标累加、绘图、梯度裁剪和序列处理。`d2l` 的简短调用隐藏了教材前面已解释的实现，阅读模型时遇到行为不明，应回到对应函数查看设备、形状及损失归一化规则。

源码存在多个框架分支及教学版本，不能只凭相同函数名推断调用签名一致。例如 `train_ch6`、`train_seq2seq` 面向不同任务；指标累计的是总和还是平均值、评估是否切换模式，都要按实际函数确认。

### 23.8 `d2l` API 文档

[原文](../../chapter_appendix-tools-for-deep-learning/d2l.md)。本节按类与函数列出接口，是查找入口的索引，而不是独立教学叙事。查阅时先确定框架命名空间，再看签名与来源章节；API 页面里有某个名称，不表示所有环境都安装了其依赖。

本部署选择 `from d2l import torch as d2l` 的 PyTorch 路线。网站保留其他框架标签页属于内容展示，不等于 MXNet、TensorFlow、JAX 学习环境已验证。遇到版本差异时应记录具体错误与实际版本，再确定修订，避免盲目降级整个环境。

## 自测与答案线索

- **浏览器刷新会清空 Python 变量吗？** 线索：变量在内核进程中，刷新页面与重启内核不同。
- **为什么网页有代码输出，仍不能认定已复现？** 线索：输出可能来自历史运行或原稿；需明确输入、环境和本次执行记录。
- **`git push` 是否意味着官方教材已更新？** 线索：取决于推送远端；个人仓库提交与上游评审是不同流程。
- **为何安装 GPU 框架还不保证所有章节可运行？** 线索：章节可能使用额外依赖、不同框架、数据资源或已变化的接口。
